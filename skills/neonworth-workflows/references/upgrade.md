# Upgrade code while preserving records

Use the [Sites profile](../../../profiles/sites/README.md) for source/build/publication and the [finance harness](../../../integrations/gpt-finance/README.md) for saved-state checkpoints. Confirm the destination, deployed version, audience and selected new release. Open the existing private source repository through the installed Sites workflow. Do not export a new instance over it or register a replacement Site.

Before changing code, establish a stable checkpoint of source, corrections, settings, review/retirement annotations, budget, planning and refresh state. A source JSON download is not a complete backup. Separate reads are not globally atomic: use the harness's stable-read verification and a host-native backup when available. Keep private backups outside public source and archives. If a required recovery capability is unavailable, disclose that limit before a destructive migration; a compatible code-only upgrade does not authorize one.

Use the implemented source updater from the clean, reviewed **new public release checkout**: `npm run sites:upgrade -- /absolute/private-instance`. The private instance must have a clean Git checkpoint and its original tracked `.openai/template.json` provenance with a known upstream revision. The helper compares that base, the new template and the private instance; it preserves uncontested local customizations and rejects conflicting dual edits, unknown provenance, symlinks and untracked collisions before changing files. Do not fabricate a base revision, replace the instance with an export or merge unrelated repository histories to bypass rejection. Resolve a real conflict explicitly and review it before rerunning.

Review the private diff and updated template provenance. The helper does not commit, build, migrate, deploy or write financial records. Keep `.openai/hosting.json`, `.openai/template.json`, storage bindings, owner-private audience, actual refresh automation and private configuration in the instance only. Preserve a recoverable clean checkpoint; if helper rollback reports incomplete restoration, keep the instance unpublished and restore that source checkpoint first. Then use the Sites build profile, run required tests/security/build gates, commit the reviewed private source and package that exact revision with the native workflow. Publish only within existing user authority; native approval requirements remain in force.

Verify the returned deployment and compare the same saved-state checkpoint afterward. Application build identity may change; financial records must not. Do not reimport, reseed, refresh history, initialize a budget or restore a backup as part of a normal code upgrade. Record and investigate any unexpected state change before further writes. For an uncertain deployment, inspect its returned ID/status before retrying.

Rollback means restoring the previously compatible code version, not overwriting current financial records. A migration or data restoration needs its own validated plan and user authority. The app's real compare-and-swap rules apply to any separately requested data write; do not invent a universal revision parameter or force a conflict.
